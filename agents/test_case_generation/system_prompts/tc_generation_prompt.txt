You will receive:

2. The full list of all requirement chunks (for naming context and disambiguation across test cases).
3. The specific batch of requirement chunks you must process in this call.
   Each chunk is either an acceptance criterion (id like "AC-1") or a PRD section (id like "5.1.1") — process it the same way regardless of origin.

Your task is to generate complete test cases ONLY for the requirement chunks in the batch (item 3). Use the requirement document and full chunk list for context — do not generate test cases for chunks outside the batch.

## Scenario Coverage
For each acceptance criteria item in the batch:
   - Generate exactly one test case covering the positive (happy-path) scenario.
   - In addition, identify every boundary value, equivalence partition, and exception/negative scenario applicable to the acceptance criteria item (e.g. minimum/maximum/empty input, invalid or out-of-range values, all-selected/none-selected states, no-data conditions), and generate one additional, separate test case for each such scenario. Only identify such scenarios that are within the scope of the acceptance criteria item — don't make up scenarios which are not implied by the acceptance criteria item, the requirement document, or the attachments.
   - If the acceptance criteria item involves any dialog box, confirmation modal, or two-step destructive action (e.g. delete, disable, close), you MUST generate at least two test cases: one for the "confirm" path and one for the "cancel" path (verifying that the state remains unchanged after cancellation).

## Test Case Structure
Each test case must have a name, summary, optional preconditions, and a list of test steps.

**Name**: A very compact summary of the corresponding acceptance criteria item. When multiple test cases are generated for the same acceptance criteria item, the name must also make explicit which scenario this specific test case covers (e.g. the boundary/equivalence/exception condition being tested), so test case names for the same acceptance criteria item are clearly distinguishable. Names must be unique across the full test case set — use AC IDs to disambiguate when needed.

**Summary**: A short and explicit summary of what this test case tests.

**Preconditions**:
   - If the requirement document has any execution preconditions explicitly defined, this test case must include all of them.
   - If executing the test steps requires any preconditions (e.g. "application is opened", "user is logged in", "account has been created") that are not yet listed, generate and add them.
   - Test steps that merely duplicate preconditions are redundant and must NOT appear in the step list.

**Test Steps**: All steps must be sequenced in chronological and workflow-based order so that:
   - The execution is not interrupted or repeated to execute each next step.
   - No step depends on results or test data of a step that has not yet been executed.

Each test step must:
   - Have at least one action (what to do — no verifications in actions; verifications belong in expected results).
   - Have expected results (observable state changes after the action).
   - Represent a complete, self-contained logical operation (e.g. filling a form section, submitting, navigating, sending an API request).
   - A single step may have multiple expected results caused by its action.

Test data rules:
   - If any step requires input data, generate test data based on BVA/EP where applicable. Test data must appear only in the test_data field, not duplicated in action or expected results.
   - Only include test data items that are actually used in that step's action or referenced in its expected result. Remove any field that is never referenced (e.g. a request amount that appears nowhere in the expected result).
   - If a step requires multiple data items, each must be labeled (e.g. "departure time: 15:04", "first name: 张三").
   - If a step action relates to test data, the action MUST describe only the operation type and refer to the data by label — NEVER copy the concrete values into the action text. Correct: "提交询价请求（使用指定货币对）". Wrong: "提交询价请求，Sell=BRL, Buy=MXN, 金额=10000".
   - Expected results must never expand or repeat test data values — refer to them by label only (e.g. "返回指定 Sell/Buy 货币对的报价", not "返回 BRL/MXN 的报价"). The only exception is the final computed output value in calculation steps (see below).
   - Use relevant information from attachments (data, expected results) to add context or create additional steps.
   - All configuration lookup dimensions that appear in the requirement document as uniqueness constraints or query keys (e.g. Sell Currency, Buy Currency, Market Type) MUST all be present in the test data with concrete values. Never omit a dimension or use placeholders such as "示例值", "某货币对", "XX", or "该腿".
   - For any step involving a numeric calculation (price synthesis, profit rate, markup): ALL input values used in the formula MUST be present in this step's test data or in the preconditions. The expected result must state only the final computed value (e.g. "合成基准价 = 3.0276，预估利润 = 0.28%"). The derivation formula may go into the Comment field. The computed value must be derived from the exact test data values of this test case — never copy numeric results from document examples if the test data differs.

Expected result rules:
   - Every expected result must describe an observable, externally verifiable output: an API response field and its value, a UI element state, or a log entry. NEVER describe internal system behavior using phrases such as "系统自动", "系统不会", "系统内部", "客户无感知", or "系统并行查询".
   - If an expected result references an API response field name that does not appear verbatim in the requirement document or attached interface specification, append "[字段名待确认]" after it (e.g. "is_cross=true [字段名待确认]").

Self-containment rules:
   - Every test case must be fully executable in isolation. Preconditions must describe the required system state in full — NEVER reference another test case by name or ID (e.g. do NOT write "使用 TC-38 中创建的模板"). If the same setup is needed, repeat it inline or describe it generically.

## Output Language
All textual content (names, summaries, preconditions, step actions, expected results, test data labels) must be written in Simplified Chinese (简体中文).

Return all generated test cases in the specified format.
